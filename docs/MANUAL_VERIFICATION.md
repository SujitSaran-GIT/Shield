# Deployment acceptance checklist

Run against an isolated deployment with real SMTP, Redis and the intended HTTPS reverse proxy. Use disposable test accounts. Do not use production credentials in screenshots, logs or shell history.

1. Back up and restore the existing database to an isolated instance. Rehearse Flyway adoption and confirm that accounts, client metadata and audit history survive. Old sessions are deliberately invalidated by V3; do not reverse one-way credential hashes.
2. Inject DB_PASSWORD, a strong JWT_SECRET, SMTP settings and a separate random APP_BOOTSTRAP_SECRET. Keep public client-admin enrollment disabled unless self-service tenant creation is intended. Configure approved CORS origins, exact trusted proxies/CIDRs and Secure cookies over HTTPS.
3. With the wrong bootstrap secret, verify rejection before any email is sent. With the correct secret, request email proof, exhaust a challenge with wrong codes, obtain a new challenge and complete setup. Attempt replay and concurrent completion; only one initial SUPER_ADMIN must exist. Remove the operator secret after setup and verify bootstrap remains closed.
4. Invite another administrator. Verify recipient email control, require confirmation by the original inviter, and let the recipient choose their own password/username. Verify expiry, revocation and replay rejection. Reload the invitation list and check lifecycle status without any credential verifier in the response.
5. Enroll two CLIENT_ADMIN accounts under the intended policy. Create an application for each. Verify generated credentials are shown once and ordinary detail/list responses contain no secret. Rotate a secret and verify the previous secret fails. Keep secrets in the integrating application's backend.
6. Register one USER per application using email proof. Verify payload role changes cannot grant administrator privileges. As CLIENT_ADMIN A, attempt reads, filtering, audit detail/activity, block, delete and credential changes against application B: all must fail. As SUPER_ADMIN, verify visibility and rejection of ordinary client-user mutations.
7. Sign in, refresh once, replay the old refresh token, and verify sessions are revoked. Test logout and password/email changes. Block/delete a USER, suspend an administrator or deactivate an application while refresh requests are running. Reactivate where permitted; old access and refresh credentials must remain invalid.
8. Test login/OTP/reset/refresh/privileged rate boundaries. Arbitrary X-Forwarded-For values must not create new identities at an untrusted peer. Verify browser-readable 429 responses include Retry-After under approved CORS. Disconnect Redis and confirm the configured fail-closed or explicitly degraded local policy; never silently disable protection.
9. Sign in from public, private, reserved and invalid IP inputs through the intended proxy. Missing GeoIP data must not prevent valid authentication. Locations must be described as approximate. Inspect retained audit/session records and verify passwords, OTPs, tokens and client secrets are absent.
10. Check every role's navigation and backend authorization separately. Check mobile (390px), tablet (768px), laptop (1366px) and desktop (1920px), including menus, dialog focus/Escape, keyboard-only use, visible focus, reduced motion and horizontal overflow. This browser verification was not executed in the agent session because browser launch permission was denied.
11. Click between users, applications, audit and health under delayed network responses. Old content must not remain under another route, tenant or filter selection. Verify loading, empty, error and retry states. Test pagination/search/sorting, permitted lifecycle controls, exports and one-time credentials.
12. Disconnect monitoring dependencies. Health views must distinguish unavailable readings from measured zeroes; public health endpoints must expose status only. Verify authorized diagnostics, request IDs, graceful shutdown, backups, retention scheduling and restore procedures.

OAuth/OIDC discovery, Authorization Code + PKCE and multiple client memberships remain architecture limitations documented in OIDC_INTEGRATION_PLAN.md. Do not market the existing confidential-client JWT API as an OIDC provider.
